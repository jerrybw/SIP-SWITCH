## 1. 背景与目标

当前生产环境为**单台 Lighthouse 同机部署**：FreeSWITCH（FS）+ Python 网关 `sip-switch-gateway` + MySQL 8 全在同一台 `Ubuntu 24.04` 上。

用户询问：若未来要把三者拆到不同服务器，改造代价多大？

本文目标：**测绘现有代码对「同机」的真实耦合面**，按组件给出改造代价与推荐拓扑，避免凭直觉高估/低估工程量。

> 拆分只是「部署底座」问题的一个子集。机制 A 解决的是「网关—FS 配置同步」这一最核心的同机耦合；剩余的拆分代价（网络 / TLS / 账号授权 / 压测）见 §4.3。真正的多 FS 节点设计与分片规则不在此文展开，见 `docs/deployment-base-design.md`。

## 2. 当前拓扑（同机，机制 A 后）

```
┌────────────────────────── Lighthouse lhins-d2k48zfu ──────────────────────────┐
│                                                                                │
│   FreeSWITCH 1.11.2          sip-switch-gateway (systemd sip-gateway :8000)     │
│   ├─ 信令/媒体/录音           ├─ 业务逻辑：路由/接入/计费/故障切换/限并发       │
│   ├─ mod_xml_curl  ──HTTP──▶ │   GET /fs/dialplan  GET /fs/directory           │
│   │  (拉 sofia.conf)         │   GET /fs/config → 返回 sofia.conf（含落地网关） │
│   ├─ ESL :8021       ◀──TCP──│   (esl_client 订阅事件、落 CDR、实时并发)        │
│   └─ sip_profiles/           └─ MySQL8 (127.0.0.1:3306, sip_switch)            │
│      external/*.xml  ←【机制A 已不写盘：网关不再写 FS 磁盘】                    │
└────────────────────────────────────────────────────────────────────────────────┘
```

**机制 A 要点**：落地网关 / dialplan / directory 的 sofia.conf 由网关 `src/fs_sofia_config.py:build_sofia_conf(db)` 生成，经 **`/fs/config` xml_curl** 动态下发。FS 仅启动时及 `rescan` 时拉一次（详见「坑位 #24：机制 A 时序依赖」）。网关侧 `fs_provision.py`（位于 `mirror/`）退化为 dev 调试用的手动回退手段，**非生产路径**。

## 3. 耦合测绘（核心结论，机制 A 后更新）

**动态控制面（dialplan/directory/CDR/并发）本来就是网络协议，一行不用改；机制 A 落地后，原先唯一的「同机硬依赖」（网关替 FS 写配置文件）也已消除。**

| 组件 | 机制 | 同机硬依赖？ | 证据 / 现状 |
|---|---|---|---|
| dialplan/directory 拉取 | FS `mod_xml_curl` → 网关 `HTTP:8000/fs/dialplan`、`/fs/directory` | ✅ 已网络原生（FS 主动来拉，网关无 FS 依赖） | `src/api/app.py` 暴露端点；FS 侧 `xml_curl.conf.xml` |
| **落地网关下发** | **机制 A**：`src/fs_sofia_config.py:build_sofia_conf(db)` 生成 sofia.conf，经 `/fs/config` xml_curl 下发 | ✅ **已网络原生（机制 A 后）** | `src/fs_sofia_config.py` / `src/api/app.py` 暴露 `/fs/config`；**不再写 `sip_profiles/external/*.xml`、不再 `rescan` 写文件** |
| CDR / 实时并发 | 网关连 FS `ESL`（`config[esl].host/port`） | ✅ 已网络原生 | `config_settings.yaml` `esl.host`；`esl_client.py` |
| 话机/接入点注册同步 | `phone_sync.py` 经 `fs_cli -H <host> -P <port> -p <pw>` 拉 `show registrations` | ✅ 已网络原生（读 `esl.host`，带 `-H`） | `src/phone_sync.py` |
| MySQL | `mysql.url = mysql+pymysql://...@127.0.0.1:3306/sip_switch` | ✅ 已 TCP；仅账号 `sip_switch@localhost` | `config_settings.yaml[mysql].url` |
| `migrate._fs_vars` / `seed_static_phones` | 读 FS 本地 `vars.xml`/`directory/` 解析 `${var}`、引导建话机 | ⚠️ 同机读；catch 后**优雅降级**空跑（非阻塞） | `src/db/migrate.py`（catch 降级） |
| `directory_xml._static_users` | 读 FS 本地 `directory/` 融合 vanilla 用户 | ⚠️ 同机读；生产 vanilla 已挪 `directory_bak`，**实质 no-op** | `src/api/directory_xml.py` |

**计费 / 路由 / 故障切换 / ESL 落 CDR 这些核心逻辑零代码改动。** 机制 A 前唯一的同机硬依赖是「网关替 FS 写配置文件」（`fs_provision.py` 一处），机制 A 已将其转为 xml_curl 动态下发，生产路径零磁盘写入。

## 4. 分项改造代价

### 4.1 MySQL 拆独立机 —— 极低（< 0.5 dev-day，零应用逻辑改动）

- `config_settings.yaml[mysql].url` 的 host 由 `127.0.0.1` 改为 MySQL 服务器内网 IP；
- 在 MySQL 服务器新建账号 `sip_switch@'<网关IP>'`（当前仅 `sip_switch@localhost` 一条），配库授权；
- 防火墙放 3306（走内网/VPC）；SQLAlchemy 已抽象，**无应用代码改动**；可顺带加 `pool_pre_ping=True`。
- 风险：跨机 DB 延迟（同 VPC 内 <1ms，可忽略）；建议 TLS 或私有网络隔离。
- ⚠️ 云数据库常无 DDL 权限：现 `db/migrate.py` 启动自动建表/加列，需区分「可建表」与「只读读写」两模式，后者须提供离线迁移脚本（见 `docs/deployment-base-design.md` §5）。

### 4.2 FS 拆独立机 —— 机制 A 后 ≈ 0（核心改造已落地）

**4.2.1 核心改造（机制 A 已实现 ✅，2026-09-07 commit `86cbaaa`）**

推荐方案「FS 经 `mod_xml_curl` 拉网关配置」**已被机制 A 落地**：网关新增 `/fs/config` 端点返回完整 `sofia.conf`（含 `<gateways>`），FS 通过 xml_curl 随用随拉——网关彻底**不再碰 FS 磁盘**、不再 `rescan` 写文件。这与现有 dialplan/directory 模型完全一致，无状态、最干净。

- 改动面（均已合入）：`src/fs_sofia_config.py`（生成 sofia.conf）+ `src/api/app.py`（暴露 `/fs/config`）+ FS 侧 `xml_curl.conf.xml` 新增 gateway binding。
- **额外收益已达成**：消除原「首部署存量网关需挨个编辑保存触发一次 `provision()`」的坑——FS 按需拉，无需启动期 provision 循环。
- 残留注意：机制 A 下 FS 仅在**启动时及 rescan 时**拉一次 sofia.conf；若 FS 先于网关数据插入启动，须补一次 `sofia profile external rescan`（坑位 #24）。

**4.2.2 遗留只读引导加固（约 0.5–1 天，低优先级）**

`migrate._fs_vars` / `seed_static_phones` / `directory_xml._static_users` 三个同机读。机制 A 后它们已**不是阻塞依赖**（配置同步靠 xml_curl），但 FS 远程时仍会 catch 降级空跑；建议加 `fs_co_located: true/false` 开关（默认 true），关掉时明确跳过，或把「种子源」改为由网关自己的 MySQL（`sip_phone` 本就在库里）提供，不再依赖 FS 磁盘。优先级低，属整洁度。

**4.2.3 网络/安全/性能（约 1–2 天）**

- ESL 与 HTTP 加 TLS（或限定私网/VPC）；
- 每通呼叫多一次 dialplan/directory HTTP RTT——FS↔网关放同区域、高 CPS 时考虑 ESL 长连 + 短 TTL 缓存；
- 多机 staging 压测（CPS/并发/故障切换回归）。
- 机制 A 后 ESL 与 xml_curl HTTP 是**唯一通信面**，拆分只需放开私网/TLS，无额外代码耦合。

### 4.3 三者全拆 —— 机制 A 后合计约 1–2 dev-day + 一套多机 staging 验证

- MySQL（<0.5d，§4.1）+ FS（核心 0d 已落地，仅剩 §4.2.2/§4.2.3 网络与加固 ≈ 1–2d）叠加；无交叉阻塞，可并行推进。
- 相比机制 A 前估算的 5–7 dev-day，**最大的一块（FS 配置同机依赖）已被机制 A 消除**，拆分可行性大幅提升。

### 4.4 常见误区：为什么不能把「路由+桥接」合并进网关、省掉 FS↔网关往返

**问法**：拆机后，呼叫流程的步骤 2（FS 经 `mod_xml_curl` 拉 dialplan）、3（网关算 candidates）、4（网关返回 `bridge` 指令）为什么不能干脆交给网关一手包办，免得 FS 和网关来回通信？

**正解：网关没有「嗓子」，FS 才有。**

| 层 | 负责方 | 职责 |
|---|---|---|
| 数据面（嗓子的活） | **FreeSWITCH** | 与话机/运营商收发音信令（SIP INVITE/200/ACK）、搬运媒体流（RTP 录音/转码/DTMF）、维护呼叫状态机、**真正执行 `bridge` 把第二腿 INVITE 发给运营商** |
| 控制面（大脑的活） | **Python 网关** | 查库算路由、计费、故障切换排序、预付费拦截、用户目录——但**不持有任何 SIP socket、不碰 RTP** |

`bridge sofia/gateway/<Name>/...` 是 FS 方言：FS 必须**自己**用本地 `external/<Name>` 凭证去 REGISTER、发 INVITE、收 200、建 RTP。Python 网关里没有任何代码能「替 FS 把这条 SIP 腿发起去」——它没有 sofia profile、没有到运营商的 socket。

所以那段「往返」的本质是**控制面/数据面接口**，并非冗余：
- **FS → 网关（xml_curl GET）**：FS 向大脑**要指令**（「按库里现状我该干嘛？」）；
- **网关 → FS（dialplan XML）**：大脑把**执行脚本**递回（「`bridge` 到运营商 X」）；
- **FS 自己执行 bridge**（含落地凭证取用）——嗓子按脚本发声；
- **FS → 网关（ESL 事件）**：嗓子向大脑**汇报**（通了/挂了/CDR）。

**「合并交给网关」缺的一步，是网关物理上发不出那通 SIP、扛不住那路 RTP。** 它不是冗余通信，而是分工的边界。

**真要消灭这段往返，只有两条路（都不是「合并」，而是换底座）：**
- **方案 A：网关用 ESL `originate` 反驱 FS（ESL 驱动模型）**——不再用 `mod_xml_curl` 拉 dialplan，FS 只留「接到呼叫就 park 并报网关」的最小 dialplan，网关侦听到新呼叫事件后下 `bgapi originate`/`uuid_transfer` 指挥桥接。效果：xml_curl 那次 HTTP 往返没了，但**换成一次 ESL 命令往返**——往返没消失，只是换通道；且网关变成每通呼叫建立的**同步总控**，延迟与可用性耦合变差，还失去 FS 原生 dialplan（C 层极快）的性能优势。一般不划算。
- **方案 B：网关自己做成 SIP B2BUA（替换 FS 的嗓子里子）**——给 Python 加 SIP 栈或前面挂 Kamailio/OpenSIPS。这才是字面意义的「合并 2/3/4」，但代价是**重写 FS 的核心价值**（媒体服务/录音/转码/状态机），等于另起产品，不是重构。

**为什么拆机反而更说明「不该合并」**：拆机只是让 FS/网关/MySQL 分处不同主机，**角色分工不变**；这段往返在 LAN/VPC 内是一次 HTTP GET（亚毫秒级），拆机后仅是跨机亚毫秒，成本可忽略。把它「合并」进网关反而要付出「网关每通呼叫都卡在关键路径 + 失去 FS 原生性能」的真实代价。

> 一句话：**网关算得出来「走哪条中继」，但只有 FS 发得出那通去运营商的 INVITE、扛得住那路语音。所以 FS 必须来问、网关必须答、FS 必须回报——这段往返是分工的接口，不是可省掉的冗余。**

## 5. 推荐目标拓扑

```
  [FS 机]                 [网关机 :8000]                 [MySQL 机 :3306]
  信令/媒体/录音   ──mod_xml_curl(HTTP)──▶   业务逻辑         ──TCP──▶   sip_switch
  (独立服务器)     ◀────── ESL(:8021) ──────┘  (独立服务器)            (独立服务器)
                  FS 经 xml_curl 同时拉
                  dialplan / directory / gateway(sofia.conf)
```

- FS 与网关的「大脑—喉咙」关系不变，仅物理分离；
- 机制 A 后网关**不再写 FS 磁盘**，FS 配置无状态、随用随拉；
- MySQL 经私网授权账号访问。
- 注意：本拓扑是「拆成 3 台」的最小形态。若 FS 要横向扩到 N 台（VOS 式分片、注册型网关按节点单选下发），见 `docs/deployment-base-design.md` §2 形态矩阵与 §3 分片规则——那是本文之上更完整的部署底座设计。

## 6. 落地优先级与风险（机制 A 后）

| 项 | 优先级 | 风险 |
|---|---|---|
| FS 拆机（xml_curl 拉 gateway） | ✅ **已完成（机制 A）** | — |
| MySQL 拆机 | 高（收益大、代价小） | 低；跨机延迟、账号授权、云库 DDL 权限 |
| 网络 TLS/压测 | 中 | 中；高 CPS 须验证 RTT |
| 遗留只读引导开关 | 低 | 低；现有已降级空跑，属整洁度 |
